## Verdict

**REMEDIATE — 0 P1, 1 P2, 1 P3.**

Do not call T23/T24 complete or advance its integration gate until the P2 is
fixed and the focused regression coverage is added. The four intended product
outcomes are substantially present; the defect is an incorrect error
classification for the already-supported non-PDF paths.

## P2 — TXT/MD read failures are misclassified as scanned PDFs

`FileChooser.svelte` declares `isPdf` inside the `try`, but its shared `catch`
always selects either `pdf_locked` or `pdf_scan`:

```js
error = isPasswordProtectedPdfError(err) ? copy.err.pdf_locked : copy.err.pdf_scan;
```

Thus a failure from `File.text()` for an accepted `.txt` or `.md` upload
renders: “It looks like a photo or a scan.” That is false, and violates the
T23 boundary that scan classification is PDF-only. It also converts a generic
local read failure into an instruction about an image-only PDF.

Reproduction in a real headless Chrome/Vite session: select a valid
`short.txt`, override that browser session's `File.prototype.text` to reject
with `Error('synthetic TXT read failure')`, then set the file input through
Chrome DevTools. The rendered `role=alert` was exactly:

> We could not find any words in that file. It looks like a photo or a scan.
> Copy your CV text and paste it instead.

Remediation: determine `isPdf` before entering the `try`; reserve
`pdf_locked` and `pdf_scan` for PDF failures only. Route TXT/MD read failures
to the product's generic safe error (or a new approved exact copy key if the
design owner supplies one). Preserve `session.resume` in that branch, and add
the regression to the permanent test suite.

## P3 — the failure matrix has no durable behavioural regression coverage

The new browser test exercises the over-cap TXT path, exact privacy text, and
state preservation for an unsupported extension. The scan, locked-PDF,
previous-state-on-PDF-failure, and downstream low-confidence notice are only
covered by source-pattern/helper assertions, not a durable component/browser
test. This left the P2 catch-all regression undetected.

Add focused tests which use an image-only PDF and a password-protected PDF
(or deterministic PDF.js task mocks), assert their distinct exact messages,
assert a pre-existing pasted `session.resume` remains unchanged after each,
and render `fitMatch.confidence === 'low'` through the practice screen to
assert the non-blocking `--note`/`role=status` presentation. Add an accepted
TXT or MD read-rejection case so the PDF-only classification boundary remains
protected.

## Acceptance evidence retained

### T23 outcome 1 — scanned/image-only PDF

Pass for PDFs. A real blank, valid PDF generated by Ghostscript was selected
through the live native input. PDF.js extracted no text and the browser
rendered `copy.err.pdf_scan` exactly. The threshold is 40 trimmed extracted
characters and is invoked only in `if (isPdf && !hasExtractablePdfText(text))`.

### T23 outcome 2 — locked PDF

Pass for the installed PDF.js API. The project pins `pdfjs-dist@6.3.289`; its
bundled `PasswordException` has the stable name `PasswordException`. A real
user-password-protected PDF generated by Ghostscript rejected from
`getDocument(...).promise`; the browser rendered `copy.err.pdf_locked`
exactly, distinct from scan copy. The `name` classifier therefore matches the
installed, browser-observed API behaviour.

### T23 outcome 3 — cap and distinct warning

Pass. A live 20,001-character TXT selection retained the first 20,000
characters, replaced the picker with `✓ long-resume.txt`, and rendered the
non-blocking `role=status` warning exactly: “Your CV was long, so we used the
first part of it. That is usually enough.” `prepareUploadedResumeText` uses
strict `>` semantics, so an exactly-at-cap value is not marked truncated.

### T23 outcome 4 — content that is not a resume

Pass for the specified chosen presentation. The actual design contract is not
a file heuristic: low `fitMatch.confidence` is the downstream signal. In a
live browser I set a low-confidence fit match and rendered Practice; it showed
the exact `copy.warn.not_cv` in a non-blocking `MessageStrip` with `kind=note`
and `role=status`, above the practice flow. This fulfils design state 8: the
advert-led questions remain usable rather than the optional CV blocking the
product. The P3 above is about absence of a permanent behavioural test, not
the displayed treatment.

### State preservation, type boundary, T24, and accessibility

- A pre-existing pasted `session.resume` remained the exact string
  `Existing pasted CV survives failure.` after a subsequent real scanned-PDF
  upload produced its alert. Assignment occurs only after successful
  extraction, normalization, and PDF text validation.
- The PDF-only under-40 check correctly leaves short TXT and MD content
  eligible to become a resume. The P2 is the separate *read-error* catch path
  described above.
- The `accept` value remains exactly
  `.pdf,.txt,.md,text/plain,text/markdown,application/pdf`; extension matching
  is case-insensitive and rejects unsupported/double extensions.
- T24's privacy wording is verbatim `copy.start.privacy`. In the live DOM it
  was always visible immediately after the picker control, in the required
  band panel; its text was exactly: “Your CV stays on your phone or computer.
  We read the words in it here in your browser. We never save it and there is
  no account.”
- The visible `Choose a file` label has a real associated native file control
  (`label.control.type === 'file'`) and supplies its accessible name. The
  existing browser regression also proves association and one native-input
  click. Alerts are `role=alert`; cap and low-confidence notices are
  non-blocking `role=status`.
